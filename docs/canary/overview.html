What canary models, runs and checks

A C library reaches a program written in another language through two package managers — one for the system, one for the language — and a binding between them. Canary models that join, runs each combination a project has, and checks what the pieces must agree on. What a run recorded is read from a separate file per machine; only §2's counts are written into the page, from the machine that last rendered it.

1. A chain, layer by layer

Nodes are what exists. An edge points from components to a component and carries one annotation. Most carry the action of ours that realizes the relation. Where we run nothing, an edge carries information in italics: whatever does establish the relation — and, while a package's recorded run is drawn, what that run recorded about it. One edge carries a claim, by its code, because a claim of ours is the only thing relating its two ends. A claim is an agreement: a row of §2, or a candidate one not yet in the registry. An edge's badges count the agreements placed on it that apply to the chain drawn — filled for those canary checks, hollow for those only named so far — so they change with the mechanism, and in a recorded run the filled one takes the colour of those agreements' outcomes. An agreement placed on several edges is counted on each. Hover an edge for what it establishes and which agreements its badges count.

Not yet every step. 10 of the catalogue's 19 action families have no edge here: fetch_source, configure, scan_sources, fetch_headers, fetch_binding_source, build_app, probe_app, fetch_app, pack_lib, pack_app — computed from the action catalogue, not listed by hand. The source fetches leave both source nodes with no producer, and adding them is a decision rather than a drawing fix: canary treats a repository as a provider beside the system and language packages, which would put it in the package layer.

How this diagram is laid out — 13 rules a redraw in any framework must keep
  1. The system side is on the left and the language side on the right: every node on the system side lies left of every node on the language side. The two package managers' worlds meet in the middle, and every edge that crosses between them is a cooperation. Each node's side is data (Canary_topology.nd_side). (user, 2026-09-24)
  2. Layers stack from the top: package managers, packages, artifacts, programs. Each node sits inside its layer's band. The chain runs from who resolves, through what is claimed, to what is on disk and what runs.
  3. A package and what it ships form one vertical line: its package manager above it, its content straight below it — native package, headers, library; binding package, stub, module, surface. On the native line the staged copy sits under the library it copies. user, 2026-09-27: "vertical line for a package and package content"
  4. Every package sits at the same height, the bridge package among them. A bridge package is a package: conf-gmp is an opam package, as libgmp-dev is an apt one. (user, 2026-09-24)
  5. Nodes of one kind on the two sides share a row: the two package managers, the two sources, headers and stub, library and module, staged copy and surface, the two consumers. user, 2026-09-24: "if they are on the same abstraction layers, they can stay on the same horizontal line"
  6. A source is not package content, so it sits beside its package's line, clear of it: the native source to the upper left of the headers, the binding source to the upper right of the stub. user, 2026-09-24: "the source is not in the package which usually contains the library or module" — drawn on the package's line, it sat on the package's edges and read as its content.
  7. The capability file is content inside the native package: it sits a level below it, off its lower right. gmp.pc ships in libgmp-dev and is written by its packager — not a package, and not the bridge's. (user, 2026-09-22 and 2026-09-24)
  8. The bridge package belongs to the language side: it sits between the two packages, nearer the binding package. user, 2026-09-24: "the bridge package should be near to the binding_package, since it belongs to the language PM's side"
  9. The two consumers sit under the side whose resolution they use: the artifact-linked one, which names paths, toward the system side; the package-linked one, which names a package, toward the language side. Which side resolved a program's inputs is the difference between the two probes.
  10. The two sides are named over their columns. user, 2026-09-24: a hint for "the left part and right part for the system and language division". A dividing line was not drawn: every edge crossing it is a cooperation, and one would carry its label on the line.
  11. No two boxes overlap. A box drawn over another hides a node.
  12. Nothing drawn hides anything else: no edge runs under a source it does not join, and no label or badge lies under a box, another edge's marks or a band's title. A mark under a box is lost, and a package's edge under a source drew the source as package content. (2026-09-24)
  13. One diagram: every chain is drawn on the same layout and switched from the panel, never drawn a second time beside it. Laid end to end, chains are compared by memory. (user, 2026-09-24, when §2's drawings were merged into §1)

Each is held against these places by overview.layout_rules_hold, or by the pin it names; the looks are the keys'.

One edge runs both ways. binding package ↔ language module is an install when the binding is fetched and a pack when it is built here. Those are different actions establishing different relations, and which one applies is a fact about the world, not about the project. Both are drawn; in any given world exactly one is live.
Two consumer programs, one source. The artifact-linked program is handed the language module and the native library by path, every input named, and answers is the code right. The package-linked program names only the binding package and lets the package manager resolve the rest, and answers is the recipe right: an install can omit a file, a META can be wrong, a conf chain can fail to resolve, and the first program sees none of it. They should be the same program, which is what makes the pair informative, and the edge between them is a claim nothing else here can make. The linking lift, planned, derives the second from the first: the same source and expected result, with only the resolution changed, from the binding mechanism and the project's static facts.
A declaration is a badge. A ◇ on a node marks what the project declares about that artifact; hover for it. Two nodes carry one, and the declaration-facing claims sit there. Such a claim fails when the world differs from what the project said it would be, which is a defect in the declaration as often as in the software.

The source is a node here; the layered model has it only in its package-rewrite cases.

1.2 The results, one row per chain

Every chain canary runs, on each machine that recorded it: a world in one language, the key §1 draws. 2. The agreements

Every agreement, where its rule RAN and where it is CHECKED, over the same frames as §1.2's result table — of which it is the template, so an empty column there can be looked up here, and ◆ marks the column each claim fills.

Two of its columns are not mechanism. decided and blame are counted from recorded runs, per agreement, so this section alone depends on run state — unlike everything else here. Splitting the table at that seam would have shown one row's halves on two pages, which is worse.
A finding does not fail its step. A violated agreement is a finding about the artifacts, so the step that read the evidence still passes, and §1.2 can show a passed step beside a violated check; --strict fails that step instead. A failed world assertion — a package pin or source ref other than the world declares — is different again: it says the run tested something other than it claims, which puts every verdict in that run in question.

checked: 6 laws, every row obeys them · no unwatched mechanism × format cell

The 6 laws every row keeps
  1. kind_matches_target_count — an ADMISSIBILITY claim ranges over two artifacts, unless one member of its tuple is a declaration standing in for an artifact; a PROMISE over exactly one; BEHAVIOUR and COMPOSITION over none
  2. promise_is_held_against_a_declaration — a PROMISE compares an artifact with what the project declared, so some method of it must reference Declared_facts
  3. object_format_narrows_or_is_empty — the object column is EMPTY unless the claim is restricted to fewer formats than exist — an axis that does not narrow says nothing
  4. an_evaluator_is_named — a row with an evaluator names it in `implemented at`, and a row without one shows no function — the red cell must mean what it says (OUR rows: an external row names a tool)
  5. external_reach_is_declared_and_possible — a tool's row states the TOOL's reach, not the claim's: at least one object format, and neither a format nor a language the claim it answers cannot have
  6. a_row_does_something — every row is either rooted somewhere or fires somewhere; a row that is neither describes a claim no action can reach

3. The model: package managers, mechanisms, cooperations

A chain is one binding mechanism (§3.2) between two package managers (two rows of §3.1), joined by their cooperation (§3.3). Each is picked per world: a package manager goes on the side its driver's scope says, the binding's declared mechanism picks its row, and the cooperation follows from where the world's artifacts come from and the gates its project declares. §3.4 lists every combination the projects' worlds have. §1 draws a combination on one fixed graph whose edges are named by actions: the mechanism sets which artifacts exist, and the cooperation which package nodes and joining edges. Every cell is computed from canary's code — the drivers, the mechanism catalogue, the bridge model, the cooperation kinds and the projects' declarations — so a table lists only what canary covers. The layered-model draft's tables were the reference for the columns; they also cover ecosystems canary does not reach yet (RPM, Cargo, Cabal, RubyGems, Conda, Nix).

3.1 Each package manager on its own

A bridge is package content. It is a package, or part of one, that exists so two package managers can cooperate — opam's conf-* packages and depexts fields — and it belongs to neither side's own content. It is optional: two package managers may cooperate through a bridge or through nothing but the artifacts, and a language package that links whatever the system installed is not thereby broken. Each package manager defines its own kinds.
A capability file is not a bridge. A .pc or META file says what a package offers — a name, a version, flags, libraries — and belongs to the package that ships it. A conf-* bridge carries a package's identity, the mapping to the system's package, and a check. The two are written by different people and can disagree, so the file is a source of claims; what holds the symbolic path to the artifacts is the bridge's check, which reads the file.
