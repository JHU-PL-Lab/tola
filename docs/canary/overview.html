How two package ecosystems are joined

General mechanism — no project, no version, no verdict in the page itself. What ran and what it decided is the result matrix; this page is what can exist, which is a different question. The one exception is §2.1, which draws a recorded run over the same layout for comparison, from a separate per-machine file.

A bridge is a thing, not a relation. It is concrete, separate package content whose purpose is package-manager cooperation. It lives in neither the pure native side nor the pure language side — which is exactly why a binding-level view cannot see it, and why this page exists. It is also optional: two ecosystems may cooperate through a bridge, or through nothing but the artifacts, and a language package that links whatever the system installed is not thereby broken.
A capability file is not a bridge. A conf-* package carries package identity plus the depext mapping, and a check. A .pc file carries capability — a name, a version, cflags, libs — and belongs to the package that ships it, as a META file belongs to its OCaml package. They are written by different people and they can disagree, which is why the file is a source of claims; but what validates the symbolic path against the artifacts is the bridge's own check, which reads the file. Each package manager defines its own kinds of bridge. Cargo's *-sys topology has no bridge and a capability file, which is what makes it artifact-centric rather than bridgeless.

1. The generic chain

Nodes are what exists. An edge points from components to a component and carries one annotation. Most carry the action of ours that realizes the relation. Where we run nothing, an edge carries information in italics: whatever does establish the relation — and, on §2.1's recorded worlds, what a run recorded about it. One edge carries a claim, by its code, because a claim of ours is the only thing relating its two ends. The badge on an edge counts the claims that sit there. Hover an edge for what it establishes.

Not yet every step. 10 of the catalogue's 19 action families have no edge here: fetch_source, configure, scan_sources, fetch_headers, fetch_binding_source, build_app, probe_app, fetch_app, pack_lib, pack_app — computed from the action catalogue, not listed by hand. The source fetches leave both source nodes with no producer, and adding them is a decision rather than a drawing fix: canary treats a repository as a provider beside the system and language packages, which would put it in the package layer.

One edge runs both ways. binding package ↔ language module is an install when the binding is fetched and a pack when it is built here. Those are different actions establishing different relations, and which one applies is a fact about the world, not about the project. Both are drawn; in any given world exactly one is live.
There are two consumer programs, not one. The artifact-linked one is handed the language module and the native library by path — every input named explicitly. It answers is the code right. The package-linked one names only the binding package and lets the package manager resolve the rest. It answers is the recipe right, which fails differently: an install can omit a file the consumer needs, a META can be wrong, a conf chain can fail to resolve, and none of that is visible to the first probe. They should be the same program — that is what makes the pair informative rather than merely two tests, and the edge between them is a claim nothing else in this graph can make.

The linking lift is the method that derives the second from the first: same source, same expected result, only the resolution changes — from inputs named by path to a package named by the consumer. It should be universal, computed from the binding mechanism plus a project's static facts (what the package is called, what the consumer imports). Where a project must customize it, the customization comes in two kinds that must not be confused: telling the lift a name it cannot derive is static information, while supplying a resolution the package failed to provide — an environment variable pointing at the native library — is the package admitting its recipe is insufficient, and is recorded as a finding.
The declaration is a badge, not a node. It used to be drawn as a box, and its position was arbitrary — nothing in the chain produces it, it takes part in no action, and no tool ever enforced it. It is the experiment's own statement about one artifact, so it is now a ◇ on the two nodes that carry one; hover for what is declared there. Those two account for all four declaration-facing claims. It also explains why they behave differently: such a claim cannot fail because two tools disagreed — it fails because the world differs from what we said it would be, which is a defect in the spec as often as in the software.
One node the three-layer picture does not have: the source, which the layered model carries only inside its package-rewrite cases, never in the base picture.

2. Concrete cases

The general shape above, instantiated: the same graph with its nodes named. A node that is absent does not exist in that case; a greyed edge exists and does not fire. Switch between them rather than scrolling — chains laid end to end are compared by memory, which is the one thing that makes them hard to compare. Both bridges present, and each sits with its author. The SYMBOLIC path runs binding → conf → depext → system package; the ARTIFACT path runs conf predicate → capability query → the library on disk. They can land on different libraries, and nothing today compares them.

The consumer package carries the native artifact. The system PM, the system package and both bridges disappear — there is no cooperation left, which is a different statement from having no bridge. Every claim that compared two ecosystems has nothing to compare.

The native side is built here, so the system package is not used. The binding package's conf-llvm-shared {= "19"} constraint is still in its depends and opam still evaluates it — against the system, which this world is not using. The gate passes or fails on evidence unrelated to the artifacts under test.

Both sides come from the same package manager, so there is no second ecosystem to bridge to — the constraint travels as an ordinary dependency in one namespace. This is torch: the library arrives through opam as an upstream binary, named directly by a depext bound rather than through a conf hop.

The binding and the library were joined by whoever built the interpreter, outside any package manager we can observe. CPython's stdlib sqlite3 is the case. The coupling is entirely real — the extension records a NEEDED on libsqlite3 and the loader resolves it — but there is no declaration anywhere to check it against. No gate and no gate mechanism are different situations.

4 edges carry no claim at all (resolve_sys, realize_hdr, realize_cap, build_hdr). Every one is a relation a real tool establishes and from which we recover nothing. Most are the package layer and the cooperation between the two ecosystems; almost everything we have sits on the two edges where a compiler or a linker ran.
The network analogy, and where it breaks. Two hosts in a network stack implement the same protocol at each layer, so both a per-layer invariant and an end-to-end invariant have a stated contract to check against. Here the horizontal relation at the package layer is a bridge somebody wrote, or nothing — not a protocol, and not symmetric between the two sides. A bridge may carry identity while dropping version, which in network terms is a layer that forwards the address and silently discards the checksum. That asymmetry is why the end-to-end invariants are the ones we do not have.
