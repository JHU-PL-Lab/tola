# Canary code audit — 2026-06-01

**Purpose.** Stocktake every file under `src/canary/` before another
reorganization pass. The recent base/surface/tool/action moves were
driven incrementally — each move felt locally right but the cumulative
result still has kitchen-sink files (`canary_basic.ml`, `canary.ml`)
and ~500 lines of dead legacy plumbing intermixed with live code. This
doc maps the current state honestly so the next pass can be planned
holistically.

**Scope.** All `.ml` files under `src/canary/`. `legacy/` is treated
as a parking lot and audited only briefly. `_out/` is build output
and excluded.

**Method.** For each module: line count, top-level definitions
(types + significant functions), outbound deps (modules opened or
qualified), inbound deps (number of distinct files referencing the
module), cohesion verdict, and the specific issues that argue for
movement / splitting / deletion.

**Cohesion legend.**
- ✅  coherent: one clear job, name matches content
- ⚠   mixed concerns: multiple themes in one file; candidate for split
- ❌  kitchen sink: many unrelated definitions; needs targeted cleanup
- 🗑  dead or legacy: no live external references; candidate for deletion / parking

## B. Cross-cutting findings

### B.1 Kitchen-sink files (high priority)

Two files account for most of the "feels wrong" smell:

**`base/canary_basic.ml`** is doing two jobs:
- Live vocabulary (artifact_kind, rule, version, project_spec, step, …)
- Dead legacy types from the retired yaml backend (job_spec,
  step_phase, canary_config, …) plus their helpers
  (`name_of_job_spec`, `mk_canary_config`, …)

The dead half is ~13 types and ~6 helpers — about 50% of the file by
LOC. Worse, it pollutes the namespace: `Canary_basic.job_spec` exists
but is dead, while `Canary_backend_gh.job_spec` is the live one with
the same name. A reader who greps for `job_spec` sees both and can't
tell which is current.

**`action/canary.ml`** mixes:
- Dead legacy (`project_config`, `verify_of_phase`, `steps_of_phase`)
- Live action_rule structure
- Live step model types
- Live path tables
- Live mermaid helpers

The legacy header alone (lines 6-66) accounts for ~60 lines of
mostly-failwith stubs. The remaining 4 topics are each coherent but
co-locating them in one 648-line file makes the file hard to read.

### B.2 Latent base → surface dependency

`base/canary_basic.ml` line 34 references `Canary_artifact_api.lang`
(which lives in surface/). The build succeeds because all modules
compile flat under one library, but the layer ordering documented in
`src/canary/dune` says base < surface.

Two ways to fix:
- Lift `lang` (and `string_of_lang`) from
  `surface/canary_artifact_api.ml` to `base/canary_basic.ml` (or a
  new `base/canary_lang.ml`). `lang` is foundational vocabulary used
  by base, tool, surface, action, backend, projects — base is its
  natural home.
- Stop documenting base as below surface and accept the cycle. Less
  honest.

### B.3 `open Canary` is now near-empty

After `rule` and `version` moved to `Canary_basic`, the `Canary`
module (action/canary.ml) is mostly action-graph data structures.
But several files still open it for convenience:
- `canary_project_tiny.ml`, `canary_project_z3.ml`,
  `canary_project_llvm.ml`, `canary_run.ml`, `canary_diagram.ml`,
  `canary_backend_gh.ml`, `canary_action.ml`

Of these, `canary_diagram.ml`, `canary_backend_gh.ml`, and
`canary_action.ml` genuinely use `action_rule` / `action_step` /
`step_expectation` — they need it. The project specs and `canary_run`
mostly use `script_spec` (which is in `Canary_action`, not `Canary`)
plus the live types from `Canary_basic`. Some of them probably no
longer need `open Canary`.

### B.4 Dead helpers that compiled-but-never-ran

In `canary_basic.ml`: `name_of_phase`, `name_of_job_spec`,
`default_template_vars`, `mk_canary_config`, `yaml_preamble_action`,
`resolve_backend_scripts`. Zero external callers. These came from the
yaml-backend era and now exist only because their types are still
declared.

In `canary.ml`: `verify_of_phase`, `steps_of_phase`. Same era.

Deleting the dead types + helpers would remove ~200 lines from
`canary_basic.ml` and ~60 lines from `canary.ml`. The remaining
content in each is genuinely live and coherent.

### B.5 `canary_toolchain.ml` mixes three sub-concerns

See the tool/ section. The build-tool primitives (cmake/ninja/dune)
added in Step 4(b) don't actually need to share a file with
`opam_spec` + `ocaml_cc_with_pkg` + `pip_install_cmd`. A targeted
extraction to `tool/canary_build_cmd.ml` would clarify both sides.

### B.6 Duplicate ADT between action/canary.ml and surface/canary_compat_run.ml

`Canary.compat_inspect_input` and `Canary_compat_run.typed_input` are
structurally identical (six constructors, different payload shape).
The translation lives in `canary_action.ml:336-354`. Same pattern would
duplicate if we add a second contract theory. A small unification
opportunity, not urgent.

## C. Where to go from here — proposed direction

Listed in order of value-per-effort.

### C.1  Purge dead code (high value, low risk)

Delete from `canary_basic.ml`: the 13 dead types, 6 dead helpers,
unused `string_of_lang` alias. ~200 lines.

Delete from `canary.ml`: `project_config`, `verify_of_phase`,
`steps_of_phase`. ~60 lines.

If we want to preserve the design-intent record (per CLAUDE.md's
"Retire legacy …" note), move the deleted declarations to
`legacy/canary_legacy_yaml_backend.ml` first, then delete the
references in live files. This keeps the legacy intent in one
honestly-named place rather than scattered.

After this purge, `canary_basic.ml` shrinks to ~260 lines of live
vocabulary; `canary.ml` shrinks to ~580 lines (still big but no
longer mixing dead + live).

### C.2  Lift `lang` to base (small fix, removes latent violation)

Move `type lang` + `string_of_lang` from
`surface/canary_artifact_api.ml` → `base/canary_basic.ml`. Update
~10 caller files (`Canary_artifact_api.OCaml` →
`Canary_basic.OCaml`, etc.). Sed-able.

This eliminates the documented layer reversal and makes the
"vocabulary in base / theory in surface" boundary actually true.

### C.3  Split `action/canary.ml` (modest effort, big readability gain)

Three new files:
- `action/canary_step_model.ml` — `version_info`, `symbol_*`,
  `compat_inspect_input`, `step_expectation`, `action_step`,
  `logger`, `step_status` (~160 lines).
- `action/canary_action_rule.ml` — `action_rule`, `store_rules`,
  `make_action_rule`, `nodes_of_action_rule` (~85 lines).
- `action/canary_path_table.ml` — `path_*`, `job_path`,
  `pattern_row`, `pp_job_path_table*` (~270 lines).

Remaining `canary.ml` keeps just the small mermaid-of-action_rule
helpers (~30 lines), or merges them into one of the above. The 7
`open Canary` references in callers would need updating but most
already `open Canary_basic` + `open Canary_action`; the bare
`open Canary` becomes obsolete in most.

### C.4  Extract `tool/canary_build_cmd.ml` (small, isolates Step 4(b))

Move `mark_step_complete`, `with_marker`, `cmake_configure_cmd`,
`cmake_build_cmd`, `ninja_build_cmd`, `dune_build_cmd` from
`canary_toolchain.ml` to a new file. ~60 lines. Project specs
update their qualified references (`Canary_toolchain.cmake_*` →
`Canary_build_cmd.cmake_*`); or keep both names by re-exporting.

### C.5  Maybe: split `canary_action.ml` (lower priority)

The 1248-line file is large but coherent — `script_spec` and
`derive_steps` belong together, and the runner is small enough to
share the file with them. A split into
`canary_action_script.ml` + `canary_action_run.ml` + 
`canary_action_run_info.ml` would yield three ~400-line files. Not
clearly an improvement unless we have a specific reason.

### C.6  Maybe: unify `compat_inspect_input` / `typed_input` (small smell, no current cost)

Single ADT shared between `action/canary.ml` and
`surface/canary_compat_run.ml`, eliminating the manual translation
in `canary_action.ml:336-354`. Easiest by lifting the unified type
to base/ or surface/. Worth doing when we touch this code for
another reason, not as a standalone task.

## D. Open questions for the next conversation

1. **Dead code: delete outright, or park in legacy/?**
   CLAUDE.md argues parking preserves the design-intent record of
   the retired yaml backend. Counter-argument: 200+ lines of unused
   types add cognitive load even when parked, and the same intent
   is already documented in CLAUDE.md prose.

2. **Should `lang` move to base now, or wait until we have another
   reason to touch surface/?** It's a 10-file sed but it's the most
   principled fix to the layer order.

3. **Is splitting `canary.ml` worth doing on its own?** Or do we
   wait for a feature that adds to one of the topics inside it?

4. **Should `canary_basic.ml` get a renaming once the dead weight is
   gone?** With dead removed, it holds: artifact vocab + rule vocab +
   misc helpers + IO-shell helpers (`run_cmd`). A name like
   `canary_vocab.ml` or several smaller files could be honest.

5. **Worth getting an external AI to review this audit + the proposed
   re-org?** If yes, this doc is ready to share. Next step would be
   "apply C.1 + C.2 in one commit" or similar narrowly-scoped first
   action that's easy to validate.
