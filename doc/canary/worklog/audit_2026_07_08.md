## Command-centralization gap (tiny baseline/prepare vs `tool/`)

Guidance requested 2026-07-08. **Do this after tiny-canary
(A2-with-factory) lands — noted here, not started.**

### The principle it's measured against

Canary is designed so a *project spec* is free of raw command detail:
build/probe/inspect verbs live in `src/canary/tool/` and specs compose
them. z3/llvm already honour this — cmake/ninja/dune route through
[canary_build_cmd.ml](../../../src/canary/tool/canary_build_cmd.ml),
opam/pip through
[canary_toolchain.ml](../../../src/canary/tool/canary_toolchain.ml),
and inspectors through
[canary_artifact_native.ml](../../../src/canary/tool/canary_artifact_native.ml) and
[canary_artifact_lang.ml](../../../src/canary/tool/canary_artifact_lang.ml).

**Provenance (why the duplication exists).** tiny's baseline/prepare
commands were ported near-verbatim from the earlier Python harness
(`doc/_legacy_code/tiny_python_harness/scenarios.py`, archived at Phase
E) as a quick way to check the ideas end-to-end. So this is a
*deliberately separate, provisional* command set that happens to
parallel the `tool/` one — not neglected code that drifted. The
intent is to **merge or purge it later** once tiny-canary stabilises;
the sub-gaps below are that merge-or-purge, not a bug fix.

Tiny's reference-cache builders do **not** yet honour it. They inline
raw compiler/inspector commands via `Printf.sprintf` + `run_shell`:

- [canary_tiny_baseline.ml](../../../src/canary/projects/canary_tiny_baseline.ml)
  — `build_c_lib` (`gcc -c -fPIC`, `gcc -shared -Wl,-soname
  -Wl,--version-script`, `ln -sf`), `build_ocaml_binding`
  (`ocamlfind ocamlopt`, `gcc` stub, `ar rcs`), `build_python_cext`
  (`gcc -shared`), and `inspect_n4`..`inspect_bpe3` (`nm -D … |
  python3 inspect_*.py`).
- [canary_tiny_prepare.ml](../../../src/canary/projects/canary_tiny_prepare.ml)
  — `build_c_lib_in` / `build_ocaml_binding_in` + its own
  `inspect_n4`..`inspect_bpe3`, all `~sandbox`-parameterised copies of
  the baseline ones.

### Three distinct sub-gaps (they are not one task)

1. **No direct-compiler family in `tool/`.**
   `canary_build_cmd.ml` covers cmake/ninja/dune only — there is *no*
   primitive for `gcc`/`ocamlfind ocamlopt`/`ar`. So unlike the cmake
   case, tiny's raw build commands have nowhere to route *today*; the
   unification must first **create** the family (a `canary_cc.ml`, or a
   direct-compile section of `canary_build_cmd.ml`): `cc_compile_obj`,
   `cc_link_shared` (soname + version-script args), `ocaml_compile`,
   `ar_archive`, `ocaml_archive`. This is the substantive half.

2. **Inspector pipelines are duplicated, not reused.**
   `tool/` already has the builders — `Canary_artifact_native.inspect_cmd`
   / `elf_inspect_cmd` and `Canary_artifact_lang.{inspect_cmd,
   mli_inspect_*, stub_inspect_*}` — but baseline/prepare re-inline the
   `nm … | python3 inspect_*.py` invocations instead of calling them.
   The reason is an **impedance mismatch**, not neglect: the tool
   builders emit "write JSON to `<output_dir>/<marker>`" commands for
   the runner/`derive_steps` path, whereas baseline/prepare want
   *capture JSON to stdout* (`capture_json`) to assemble the reference
   cache. Unifying means giving the tool builders a stdout/capture
   variant (or a shared inner command that both the marker-writer and
   the capture path wrap). Decide that shape before touching callers.

3. **baseline ↔ prepare duplicate each other.**
   baseline already introduced a `paths` record with `sandbox_paths`
   *specifically so both could call one set of build primitives* (see
   its own comment at
   [canary_tiny_baseline.ml:24-27](../../../src/canary/projects/canary_tiny_baseline.ml#L24)),
   but prepare never adopted it — it re-hardcodes `build_*_in ~sandbox`
   instead. Even before the `tool/` extraction, baseline's build/inspect
   functions could be parameterised on `paths` and prepare could call
   them with `sandbox_paths`. Cheapest first step; shrinks the surface
   the `tool/` extraction later has to move.

### Caveats for whoever does it

- **Keep the "owner decides the build" rationale.** tiny uses direct
  compilers *on purpose* (it's canary-owned, not upstream — see
  [canary_tiny_baseline.ml:121-145](../../../src/canary/projects/canary_tiny_baseline.ml#L121)
  and `tiny_migration.md` §1b). The new primitives should be a
  first-class *direct-compile* family, **not** a push to make tiny go
  through cmake/dune. z3/llvm/sqlite still shell out to their own build
  systems; tiny stays direct.
- **Portability dividend.** baseline hardcodes `nm -D` (Linux-only);
  `Canary_artifact_native.nm_cmd` already picks `nm -g` on macOS.
  Routing tiny's inspectors through the tool builder fixes a latent
  macOS break for free — relevant to the CLAUDE.md macOS scopes.
- **Recommended order:** (3) share baseline↔prepare via `paths` →
  (1) extract the direct-compile family into `tool/` → (2) reconcile
  the inspector capture-vs-marker shapes last. Each step keeps the
  reference cache byte-stable, so diff against a known-good
  `prepare-all` run after each.
- Relates to open TODO **#18** (audit specs for hardcoded shell
  commands routed through named primitives) and **#47** (unify
  store-selection patterns) — same "centralize in `tool/`" thrust.

### F. `src/binding/` ↔ `canary/tool/` duplication — direction (no hurry)

The user's framing, confirmed against the tree: `src/binding/` is a
**general, record-like abstraction over tool/artifact interfaces**
(public lib `tola.binding`), built on **native OCaml compiler-libs**
(`Objinfo`, `Cmi_format`, `Fl_metascanner`) + `ldd`/Mach-O parsers —
*not* shelling out. Canary saw this abstraction and wrote its **own**
implementation in `canary/tool/` that **shells out** (`nm | python3
inspect_*.py`, `ocamlobjinfo`) instead. So there is a genuine
overlap — but only in specific slices:

| `src/binding/` (compiler-libs / native) | ≈ `canary/tool/` (shell + python) | overlap |
| --- | --- | --- |
| `ocamls.ml` (`Objinfo` on `.cmxa/.cma`), `ocaml_files.ml` (file classification) | `canary_artifact_lang.ml` (`ocamlobjinfo`, `inspect_ocaml.py`, mli/stub) | OCaml binding inspection |
| `shared_library.ml` (`ldd` linked-dep), `macho.ml` (Mach-O) | `canary_artifact_native.ml` (`nm`, `is_macos`) | native lib / loader inspection |
| `opam.ml`, `package.ml`, `compilers.ml` | `canary_pm_opam.ml`, `canary_toolchain.ml` | opam / toolchain |
| `platform.ml`, `config.ml` | `canary_store.ml` (`distro`), `is_macos` | platform detection |
| `resolve.ml` (`Via_name`/`Via_value`) | watchlist vs content-hash matching | resolution strategy |
| `canary.ml` (417 LOC — the *old* canary model) | all of `src/canary/` | conceptual ancestor |

**Critical fact for whoever merges:** the **active** canary layer does
**not** use `Binding.*` at all. The `binding` library is linked only by
`src/langs/`, `src/bin/`, and the **parked** `src/canary/legacy/`
(`example_sp.ml`) — see `src/canary/legacy/dune`. So today canary/tool
is a full re-implementation, not a consumer. CLAUDE.md's existing
Known-Gap already flags "migrate `src/binding/` inspectors into canary"
but frames it **one-directionally** (absorb into canary).

**Direction (record only — no change now):**

1. Prefer **shared dependency over wholesale absorption.** Because
   `tola.binding` is a public lib other projects consume (`langs/`,
   `bin/`), folding it *into* `canary/` would strand those consumers.
   If the merge happens, the shape is more likely "canary/tool depends
   on `tola.binding` for the OCaml-deep inspectors" than "move the
   files under canary."
2. **The two are complementary, not strictly redundant.** binding/ is
   OCaml/compiler-libs-deep (richer `.cmxa` internals, no python dep);
   canary/tool deliberately shells out so it stays **language-agnostic**
   (python/rust/java plug in as data) and **macOS-portable** via the
   `inspect_*.py` scripts. The genuine duplicate is narrow: the OCaml
   (`ocamls`/`ocaml_files` vs `canary_artifact_lang`) and native-lib
   (`shared_library`/`macho` vs `canary_artifact_native`) slices only.
   Everything else is parallel-but-differently-scoped.
3. **Sequencing:** leave duplicated while canary is self-contained and
   under active development. Revisit when the "migrate src/binding into
   canary" gap is actually picked up, and at that point treat it as an
   *extract-shared-interface* task (both canary and non-canary consumers
   depend on it), guided by the mapping table above — not a fold.
4. Check `src/binding/canary.ml` (the 417-LOC *old* canary model)
   before re-implementing anything: it predates the current framework
   and CLAUDE.md already warns to "check overlap first."
