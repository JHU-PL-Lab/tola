## 2. The terms: one set in all places (user, 2026-10-07)

- On each side, three components:
  - **M**, the package manager;
  - **P**, the packaging: what a package declares (its metadata, its
    capability file, a bridge);
  - **A**, the artifacts: the **payload** a package carries, or what
    a build makes.
- Between the sides, two joins: **Co_op** and **B_mech**. They
  **relate**. Then there is the program.
- A **bridge** and a **capability file** are packaging. "Package
  content", in its old loose sense, is gone.

## 3. Open: the cooperation table (§3.3, `tab-cooperation.html`)

Agreed with the user, **not built yet**.

- **Title**: "Cooperations, with or without package managers" (the
  user's). "Cooperation" then has its broad sense everywhere: Figure
  3's description of Co_op and §0's term must say "through their
  package managers, or without them".
- **Two row groups**: with package managers, and without.
- **The kinds**, renamed. Each has a *vehicle* and *variants*:

  | kind | was | vehicle | variants |
  | --- | --- | --- | --- |
  | bridged | conf package | a bridge package (`conf-*`), or a depext field | its check: pkg-config presence, a version bound, a compile test, none; ⚠ stale |
  | repackaged | one package manager | a package in the other side's manager | native library into the language PM (Conda, opam's `libtorch`); binding into the system PM (Debian's `python3-*`) |
  | bundled | absorbed | the binding package | the library (z3-solver and llvmlite wheels), its source (opam's `z3`), headers |
  | built in | no PM between | the interpreter's distribution | — (Python's `sqlite3`) |
  | discovered | artifacts only | the binding's own build | pkg-config, a `*-config` script or CMake, search paths |

  "Stale" is the old "gated, local library": a bridge that still
  checks the system while the world's library comes from elsewhere.
  "Local" is **not a kind**. It is canary's development worlds, where
  both sides are built from source, and gets a note. In the wild the
  same shape is a bundled source (a Cargo crate's `bundled` feature).
- **The columns**: two header rows, one short term per cell (at most
  48 characters, held by a test as in Table 10), grouped in two parts:
  - **the kind**, which is general: vehicle, variants, how a version
    constraint travels, where it meets the artifacts, and **in the
    wild** (the ecosystems: opam, Cabal, Conda, Nix, Debian, PyPI,
    Cargo);
  - **canary**, which is canary's coverage: used by, and what it
    records. A kind or variant canary does not run still gets its
    row, with "—" here.

  Projects carry a ‡ where their conf package bounds the library's
  version (llvm, zstd). The foot says that 13 of the 370 conf packages
  in opam's repository bound one.
- **§1's cooperation note** is composed from the short fields, so no
  second prose is left to drift.
- **The draft's names** (`co_draft`) leave the table. They stay in the
  code as a map from the draft's terms until the prose has the new
  ones.
- **pkg-config** is a query tool that reads the system side's
  capability files (P_sys) for the language side: a bridge's check, or
  a build. It is not a component. It is Figure 2's *discover* edge,
  and it appears in the table as a variant.

**Still open**:

- Is "stale" a variant of bridged, or a row of its own (the one
  irregular use of a cooperation *with* package managers)?
- **"Gate"**: keep it and add it to §0's terms, or say "the bridge's
  check" everywhere? The code has `pm_dep_gate`,
  `gate_admits_the_world` and `Co_gated_local`. A gate is a check that
  decides whether a binding package may install: opam's `conf-*`
  packages are gates.
